# tnt-mutants: мутационное тестирование Lua-кода

## Зачем

Покрытие строк говорит, что строка выполнялась. Оно молчит о том, проверил
ли её кто-нибудь: тест, который зовёт функцию и не смотрит на ответ, даёт
те же сто процентов, что и тест, который сверяет каждую ветку. Мутационное
тестирование задаёт второй вопрос: если строку сломать — подменить `>`
на `>=`, `and` на `or`, `true` на `false`, число на соседнее, — заметит ли
поломку хоть один тест. Мутант, которого никто не заметил, — это строка,
у которой проверки нет, какое бы покрытие ни показывал отчёт.

Первый же прогон по коду со стопроцентным покрытием обычно находит
несколько таких строк: границу диапазона, которую проверили только
с одной стороны, флаг, чьё значение никто не сверял, условие, оба
исхода которого ведут к одному ответу.

Планка — 100 % убитых мутантов по проверяемым файлам. Ниже ста процентов
планка не имеет смысла: она означает «какие-то строки можно не проверять»,
а какие именно — решает случай.

## Как устроен прогон

Зрелого мутационного тестера для Lua нет, поэтому утилита собрана
из языконезависимого генератора и анализатора мутантов (universalmutator)
и своего набора правил `rules/lua.rules`. Встроенный универсальный набор
написан под C-подобный синтаксис: он ломает Lua на комментариях `--`,
неравенстве `~=` и словах `and`/`or`/`not`.

Прогон по каждому файлу идёт так:

1. **База.** Набор проверок файла гоняется на исходном коде и обязан
   пройти. Меряется его длительность — по ней выбирается предел времени
   на одного мутанта. База идёт один раз на каждый различный набор,
   а не перед каждым файлом.
2. **Сверка списков.** Правила исключения этого файла сверяются с его
   строками; ищутся слепые места генератора.
3. **Генерация.** По правилам из исходника получаются мутанты — копии
   файла с одной подменой в одной строке. Каждый мутант проверяется
   на загрузку (`tarantool -e "assert(loadfile(...))"`): не загрузившийся
   отбрасывается как негодный.
4. **Анализ.** Каждый годный мутант по очереди подменяет исходник, и на нём
   гоняется набор до первого падения (`luatest -f`). Падение — мутант
   убит. Зелёный набор — мутант выжил. Исходник возвращается на место
   после каждого мутанта.
5. **Приговор.** Доля убитых сравнивается с порогом; выжившие названы
   с diff. Файл с выжившими, слепым пятном, нулём мутантов или мёртвым
   правилом исключения — отказ. Прогон продолжается по остальным файлам,
   и итог перечисляет все отказы разом.

Код выхода — ноль только при выдержанном пороге по всем файлам без
единого отказа.

## Установка

Нужны bash 5.0 или новее (длительность базы меряется по `EPOCHREALTIME`),
Python 3, `tarantool` и luatest в проекте (`.rocks/bin/luatest`).
Для самопроверки — ещё `tt`, которым ставится luatest в каталог утилиты.

```sh
git clone https://github.com/tnt-skein/tnt-mutants.git
cd tnt-mutants
make setup
ln -s "$PWD/bin/tnt-mutants" ~/.local/bin/tnt-mutants
```

`make setup` создаёт `.venv` с universalmutator закреплённой версии
(`requirements.txt`) и ставит luatest в `.rocks` утилиты. Утилита находит
свои файлы от своего пути, поэтому ссылка в `PATH` — обычный способ
запуска; можно и звать по полному пути.

Проверить установку: `tnt-mutants selftest`.

## Запуск

Из корня проекта:

| Команда | Что делает |
|---|---|
| `tnt-mutants` | прогон по файлам, изменённым относительно базовой ветки |
| `tnt-mutants a.lua b.lua` | прогон по указанным файлам |
| `tnt-mutants --list` | назвать файлы, которые проверил бы прогон без аргументов |
| `tnt-mutants --config ФАЙЛ …` | взять настройки из другого файла |
| `tnt-mutants selftest` | самопроверка на файлах-образцах |
| `tnt-mutants --help`, `--version` | справка и версия |

**Что считается изменённым.** Три источника разом: коммиты этой ветки
поверх базовой (`MUTANTS_BASE`, по умолчанию `origin/main`), правки
в индексе и рабочем дереве и новые файлы, ещё не добавленные под
версионирование. Иначе проверка молчала бы ровно тогда, когда она нужнее
всего — пока код пишется и ещё не закоммичен. Базовая ветка недоступна —
проверяется весь прикладной код, о чём прогон предупреждает.

Явно названный файл, которого нет, — отказ: опечатка в пути иначе
давала бы «проверять было нечего» с нулевым кодом. Удалённый файл
из списка изменений пропускается — проверять в нём действительно нечего.
Ведущее `./` у явного пути снимается: списки проекта сравнивают путь
буквально, и `./a.lua` не нашёл бы правил, заведённых для `a.lua`.

## Настройки

Файл `mutants.conf` в корне проекта читается bash: значения — обычные
присваивания, список исходников — массив, правило выбора набора —
функция. Образец с комментариями — `mutants.conf.example`. Любая настройка
задаётся и переменной окружения с тем же именем; окружение старше файла,
так что разовый запуск подменяет что угодно, не трогая файл.

| Настройка | Умолчание | Смысл |
|---|---|---|
| `MUTANTS_BASE` | `origin/main` | базовая ветка для списка изменённых файлов |
| `MUTANTS_MIN_MSI` | `100` | порог убитых мутантов, проценты |
| `MUTANTS_SOURCES` | весь Lua-код без `test/` | что считается прикладным кодом: массив pathspec для git |
| `tests_for` | ближайший `test/` вверх по дереву | функция: путь файла → набор проверок (аргументы luatest) |
| `MUTANTS_SUITE` | — | один набор для всех файлов прогона, старше `tests_for` |
| `MUTANTS_LUATEST` | `.rocks/bin/luatest` | чем гонять проверки |
| `MUTANTS_LUATEST_FLAGS` | `--shuffle none -f` | аргументы luatest в прогоне |
| `MUTANTS_LUA` | `tarantool` | чем проверять, что мутант загружается |
| `MUTANTS_IGNORE` | `mutants.ignore` | список правил исключения |
| `MUTANTS_EMPTY_LIST` | `mutants.empty` | список файлов, где мутировать нечего |
| `MUTANTS_TIMEOUT` | — | явный срок мутанта, секунды |
| `MUTANTS_DEFAULT_TIMEOUT` | `15` | срок мутанта, когда явного нет |
| `MUTANTS_BASELINE_LIMIT` | `300` | сколько ждать базу, секунды |
| `MUTANTS_WORKDIR` | `var/mutants` | рабочий каталог |
| `MUTANTS_VENV` | `.venv` утилиты | окружение Python с universalmutator |
| `MUTANTS_RULES` | `rules/lua.rules` утилиты | файл правил мутаций |
| `MUTANTS_VARDIR` | `/tmp/t-<число от пути>` | каталог узлов luatest |
| `MUTANTS_MACHINE_LOCK` | `/tmp/tnt-mutants-machine.lock` | общий замок машины |
| `MUTANTS_QUEUE_WAIT` | `3600` | сколько ждать очереди на машину, секунды |
| `MUTANTS_CONFIG` | `mutants.conf` | путь файла настроек |

**Прикладной код.** Каждый шаблон `MUTANTS_SOURCES` уходит git отдельным
аргументом — фигурные скобки git не раскрывает, и перечисление в одной
строке молча не совпало бы ни с чем. Каталоги проверок в список
не входят: мутировать проверки незачем. Файлы-образцы с выжившими
по замыслу, если такие есть в проекте, тоже исключаются — обычный прогон
валился бы на них.

**Набор проверок.** Модуль проверяется набором своего пакета: он тот же,
что отвечает за покрытие модуля, а прогон всего проекта вместо него
удлиняет проверку одного файла в разы. Умолчание — ближайший каталог
`test/` вверх по дереву: `libs/<пакет>/test/` для модуля пакета, `test/`
для остального. Файл, для которого набора нет, — отказ до того, как
прогон что-либо тронул. Проект с другой раскладкой задаёт функцию
`tests_for` в `mutants.conf`: она печатает набор и возвращает ноль,
ненулевой код значит «набора нет».

```sh
tests_for() {
    case "$1" in
        # Точка входа в корне — своим набором, если он есть.
        *.lua)
            if [ "${1#*/}" = "$1" ] && [ -f "test/integration/${1%.lua}_test.lua" ]; then
                echo "test/integration/${1%.lua}_test.lua"
                return 0
            fi
            ;;
    esac

    case "$1" in
        src/*) echo 'test/' ;;
        libs/*/*)
            package="${1#libs/}"
            echo "libs/${package%%/*}/test/"
            ;;
        *) return 1 ;;
    esac
}
```

**Аргументы luatest.** Прогон под мутантом идёт до первого падения:
первое падение решает, что мутант убит, и остаток набора ничего
не добавит. Выживший проходит набор целиком — приговор тот же, а набор
со стендами из нескольких узлов не гоняется до конца на каждом мутанте.
Флаг именно короткий, `-f`: справка luatest обещает и `--failure`,
но разбор аргументов знает только `-f` и `--fail-fast`. С `--failure`
luatest падал «Unknown option» за долю секунды, каждый мутант числился
убитым, и прогон показывал сто процентов, не запустив ни одной проверки.
Теперь такая поломка — отказ базы (ниже).

## Правила мутаций

`rules/lua.rules` — регулярные выражения вида `образец ==> замена`,
по одному на строку. Генератор применяет каждое к каждой строке файла
и на каждое совпадение делает мутанта. Замена `DO_NOT_MUTATE` глушит
строку целиком.

Что мутирует: сравнения (`==`↔`~=`, `<`→`<=`/`>`, `>=`→`>`/`==` …),
связки (`and`↔`or`, `not` снимается), логические константы, проверки
на `nil`, арифметика (`+`→`-`/`*`, `-`→`+`, `*`→`+`, `/`→`*`), числа
(`n`→`0`, `n+1`, `n-1`), возврат (`return x`→`return nil`).

Что заглушено и почему:

- комментарии и аннотации типов (`--`), подключения модулей
  (`local x = require`) — правки в тексте, а не в логике; без этого
  до половины мутантов были бы такими;
- `return Module` — подмена таблицы модуля ломает подключение целиком,
  валится любая проверка, и такой мутант ничего не проверяет;
- `return nil` — правило раннего выхода превращает его в него же;
- конкатенация `..` — подмена на арифметику даёт мутанта, который
  валится на любом входе.

Любой другой возврат — `return true`, `return value` — это развилка,
и её поломку обязан заметить тест. Глушитель любого возврата одного
слова прятал бы их все, и прогон показывал бы сто процентов
по непроверенным веткам.

⚠ **Правила — регулярные выражения Python, а не шаблоны Lua.** Классы
вида `[^%w_]` в Python означают «не `%`, не `w`, не `_`», и подмена `or`
на `and` срабатывала бы внутри слов, превращая `error` в `errand`. Границы
слов задаются `\b`.

⚠ **Мутации попадают внутрь строковых литералов.** Генератор не понимает
Lua-строк, поэтому сообщение вида `'<таблица>'` порождает мутантов
с подменой `<` на `>`. Это не проверка логики, а шум; угловые скобки
и знаки сравнения из сообщений лучше убрать.

Правило, которое генератор отбросил — не разобралось как выражение или
не похоже на «образец ==> замена», — останавливает прогон сразу: сломанная
мутация иначе не порождала бы мутантов ни в одном файле, а сломанный
глушитель перестал бы глушить, и итог всё равно был бы зелёным. Правка
правил проверяется самопроверкой.

## Списки проекта

### Правила исключения: `mutants.ignore`

Некоторые мутанты неотличимы: `s:sub(0, n)` и `s:sub(1, n)` в Lua дают
одно и то же, `error(message, 0)` и `error(message, -1)` — тоже. Такого
мутанта не убить ни одним тестом, и строка исключается правилом.

Формат — путь файла от корня проекта, пробел, регулярное выражение Python
для строки этого файла; строки с `#` и пустые пропускаются:

```
# Уровень броска: 0 и -1 в Lua значат одно и то же — место вызова
# не приписывается ни при том, ни при другом, и брошенное выходит
# побайтово тем же.
src/journal/fail.lua ^\s*error\(message, 0\)$
```

Правило действует только в своём файле: перед генерацией из общего списка
берутся строки проверяемого файла, путь отрезается, и генератору уходят
одни выражения. Плоский список — выражения без путей — глушил бы такие же
строки во всех остальных файлах, и прогон показывал бы сто процентов
по строкам, которых никто не проверял.

Строка, в которой выражение нашлось, не мутирует вовсе — снимаются сразу
все подмены в ней, а не одна. Генератор ищет выражение в любом месте
строки, поэтому правило описывает строку целиком, от `^\s*` до `$`:
без якорей оно заглушит и любую другую строку файла с тем же куском.

**Исключение — последнее средство.** Каждое правило — место, которое
проверка больше не стережёт. Неотличимого мутанта чаще убирает
переписанная строка (приёмы ниже). Правило, без которого не обойтись,
заводится с комментарием над ним: комментарий доказывает, что мутант
неотличим на любом входе, и объясняет, почему строку не переписать.
Без него правило нельзя перепроверить, и оно остаётся в списке навсегда.

**Мёртвое правило — отказ.** Перед генерацией правила файла сверяются
с его строками тем же поиском, что у генератора. Правило, не совпавшее
ни с одной строкой, и правило, которое не разбирается как выражение
Python, не глушат ничего: строку, ради которой правило заводилось,
переписали, она снова даёт неубиваемых мутантов, а само правило ждёт,
пока совпадёт с какой-нибудь новой строкой того же файла, и молча её
ослепит. Такое правило валит прогон по файлу; анализ при этом идёт
до конца, чтобы были видны выжившие на бывшей строке правила:

```text
   ОШИБКА: правила mutants.ignore не совпадают ни с одной строкой файла — мёртвые: 1
     mutants.ignore:39: ^\s*local head = utf8\.sub\(text, 1, M\.SHOWN\)$
   ...
Мутационная проверка не пройдена (1):
  src/journal/format.lua — мёртвые правила исключения: 1 (строки mutants.ignore: 39)
```

Как чинить — по порядку:

1. Мутант на новой строке убивается кодом или проверкой — переписать
   строку и снять правило вместе с комментарием над ним.
2. Мутант по-прежнему неотличим — исправить выражение под нынешнюю
   строку, а комментарий — под её новый вид.
3. Строки больше нет — снять правило.

Правило правят или снимают в той же правке, что меняет его строку: иначе
прогон откажет на первом же запуске по этому файлу.

**Широкое правило названо.** Правило, совпавшее больше чем с одной
строкой, названо вслух со списком номеров строк, но прогон не валит:
такое правило бывает законным (одна и та же неотличимая запись
в нескольких местах файла), только каждая его строка не мутирует вовсе.

**Устаревшее правило.** Правило, чей файл исчез, названо перед базой
(«правило исключения ссылается на исчезнувший файл»): однажды по тому же
пути появится новый файл, и правило его ослепит. Это предупреждение,
не отказ.

Путь сравнивается буквально, в том виде, в каком файл передан прогону.
Список без настройки ищется под именем `mutants.ignore` в корне проекта,
и его отсутствие — не отказ; список, названный явно, обязан существовать:
опечатка в пути иначе молча сняла бы все правила.

### Файлы без мутантов: `mutants.empty`

Ноль мутантов неотличим от слепоты генератора: пара `/*` в шапке файла,
сломанный глушитель, опечатка в пути — и файл тоже даёт ноль. Поэтому файл
без мутантов — отказ, а не пропуск. Файл, где мутировать действительно
нечего (фасад из одних подключений, регистрация из одних строк),
записывается в `mutants.empty` — по одному пути на строку, с объяснением
строкой выше:

```
# Фасад: подключения подмодулей в поля таблицы и её возврат.
src/journal/init.lua
```

Запись о файле, у которого мутанты появились, прогон велит убрать: иначе
однажды она молча пропустит настоящую слепоту этого файла. Запись
с исчезнувшим путём названа вслух.

## База и предел мутанта

**База идёт тем же исполнителем, что и мутанты.** До всех мутантов каждый
различный набор проверок один раз гоняется на исходном коде — тем же
сгенерированным исполнителем (`var/mutants/run-tests.sh`) и той же
строкой запуска — и обязан пройти с нулём. Иначе каждый мутант
«убивался» бы теми же падениями, и итог показывал бы сто процентов
на сломанных тестах. База перед каждым файлом гоняла бы набор впустую
столько раз, сколько файлов у пакета, а красный набор или тесный предел
вскрывались бы на том файле, до которого прогон доходил через час.

Отказ базы бывает четырёх видов, и каждый назван своими словами:
проверки падают; строка запуска сломана и luatest не начал прогон;
набор не уложился в ожидание базы (`MUTANTS_BASELINE_LIMIT`, 300 с —
похоже на зависание); явный срок мутанта тесен для набора.

**Предел мутанта — не короче двух длительностей базы.** Мутант, убитый
пределом времени, числится убитым: зависание под мутантом — это
обнаружение. Но выживший мутант проходит набор целиком, как база, и если
набор идёт почти весь предел, первая же задержка машины убивает выжившего
пределом — прогон показывает сто процентов, ничего не проверив.

Поэтому база идёт со своим, долгим ожиданием, и её длительность
меряется. Предел прогона под мутантом — срок минус секунда (таймаут
анализатора на секунду длиннее, чтобы к его сроку гасить было уже
нечего), по умолчанию 14 с. Если база идёт дольше половины предела:

- срок по умолчанию поднимается для этого набора до трёх длительностей
  базы, округлённых вверх, — «предел мутанта поднят с 14 до N с»;
- явный `MUTANTS_TIMEOUT` — выбор человека, его утилита не трогает,
  а отказывает до генерации мутантов, назвав каждый тесный набор и срок,
  которого хватит всем:

```text
$ MUTANTS_TIMEOUT=2 tnt-mutants src/journal/writer.lua
── база: test/
   набор зелёный за 4.7 с
Набор test/ идёт 4.7 с при пределе 1 с (MUTANTS_TIMEOUT=2): мутанты будут убиты по времени.

Мутационная проверка не начата: предел мутанта 1 с (MUTANTS_TIMEOUT=2)
короче двух длительностей базы у наборов: 1.
   ...
   Задайте MUTANTS_TIMEOUT не меньше 16, сузьте набор (MUTANTS_SUITE)
   или снимите MUTANTS_TIMEOUT — тогда предел поднимется под набор сам.
```

Срок — целое число секунд больше нуля; дробь или слово — отказ
до прогона. Мутанты, убитые пределом, записываются в
`var/mutants/timeout-<файл>.log`, а прогон называет их число («убито
пределом времени: N»). Это не отказ, но много таких при запасе вдвое —
повод посмотреть список: там либо мутанты, сломавшие условие выхода,
либо машина, которой не хватило и запаса.

**Отказ запуска — отказ проверки, а не убитый мутант.** Анализатор знает
одно: ненулевой код значит «убит». Исполнитель поэтому сам узнаёт, что
luatest не начал проверок: оболочке нечем его запускать (коды 126 и 127)
или раннер luatest отказал сам — в разборе аргументов, в настройке прогона
или в своих внутренних проверках; такое сообщение начинается с места
в `luatest/runner.lua` (строки стека с тем же файлом в счёт не идут: они
есть и у отказа загрузки проверок, а его под мутантом вызывает сам
мутант, и это честное убийство). Такой прогон пишется в журнал
`var/mutants/launch-<файл>.log`, и файл получает отказ «проверки
не запустились на мутантах: N» — даже если анализатор насчитал сто
процентов.

Под это же слово попадает мутант, который съел память: обход,
зациклившийся с накоплением, роняет обработчик ошибок luatest, и раннер
падает у себя. Мутант здесь обнаружен, но утилита честно не отличает это
от сломанного запуска; лечится строка — шаг цикла, который мутант
не может оставить на месте.

## Слепые пятна генератора

⚠ **`/*` и `{-` в любом месте строки — даже в комментарии Lua — прячут
от генератора всё до `*/` или `-}`.** Эвристика комментариев у генератора
языка не знает: она C-шная и Haskell-ская и в правилах не отключается.
Слепа и сама строка с парой, и всё ниже неё до строки с закрывающей парой
включительно, а без закрытия — до конца файла; так же генератор понимает
метку `@BEGIN_TEST_CODE`. Образец пути `app/models/*.lua` в комментарии
шапки способен оставить от семидесяти мутантов два.

Прогон ищет пары до генерации и называет строки с ними предупреждением.
Затем правила применяются дважды кодом самого генератора, с теми же
исключениями файла: к строкам как есть и к строкам, где пар не видно.
Строки, где мутанты есть только во втором случае, названы поимённо,
и файл получает отказ «слепое пятно генератора»; анализ видимой части
при этом идёт до конца. Обход: в литерале разбить пару конкатенацией
(`'/' .. '*.xlog'`), в комментарии — писать словами («файлы каталога
`app/models`»). Грубая сверка сверху: если мутанты кончились раньше 70 %
файла, прогон предупреждает и об этом.

⚠ **Строка, которую генератор счёл мёртвой, названа, но не валит
прогон.** Прежде чем мутировать строку, генератор проверяет её наспех:
подменяет всю строку мусором и компилирует файл. Скомпилировалось —
строка объявлена комментарием или мёртвым кодом, и все её мутанты
выбрасываются. Одиночное имя или число внутри многострочного вызова
(уровень `0` у `error(...)` на своей строке) превращается в законное
выражение, и поломку уровня не проверит никто. Прогон печатает «генератор
пропустил строк: N» с номерами; обход — собрать аргумент в `local`
строкой выше, чтобы вызов стоял одной строкой.

## Приёмы против неотличимых мутантов

Мутант неотличим, когда подмена даёт тот же ответ на любом входе. Такую
строку чаще всего можно переписать так, чтобы числа или сравнения,
у которых есть неотличимый мутант, в ней не было:

- **срез от начала — отрицательным индексом:** `s:sub(-#s, n)` вместо
  `s:sub(1, n)`, `utf8.sub(s, -counted, n)` вместо `utf8.sub(s, 1, n)`
  (`counted` — `utf8.len(s) or #s`). У единицы мутанты `0` и `1-1` дают
  ту же строку, а у `-#s` единственный мутант `+#s` не проходит загрузку.
  Ответ тот же на любой строке, включая пустую и битую: слишком далёкое
  отрицательное начало оба среза прижимают к первому знаку;
- **срез до длины, у которого важен конец, — с конца:** `utf8.sub(s, -max)`
  вместо `utf8.sub(s, 1, max)`; числа-начала у среза с конца нет. Длина
  меньше единицы — отдельной веткой: `-0` берёт строку целиком;
- **поиск без начала:** `s:find(PATTERN)` по экранированному образцу
  вместо `s:find(literal, 1, true)` — у начала `1` те же неотличимые
  мутанты. Когда нужен именно поиск «как есть», начало пишется `nil`:
  `s:find(delimiter, nil, true)` ищет с начала, и числа, которое можно
  сдвинуть, нет. Так же проверяется начало строки, когда условию нужен
  свой мутант: `s:find('^//') ~= nil` вместо `s:sub(1, 2) == '//'` даёт
  убиваемый `== nil`;
- **начало и хвост строки — расширениями Tarantool без чисел
  и шаблонов:** `s:startswith('/')` вместо `s:sub(1, 1) == '/'`,
  `s:endswith('/')` вместо `s:sub(-1) == '/'`, `s:rstrip('/')` вместо
  `s:gsub('/+$', '')` (у квантификатора `+` мутанты `-` и `*` снимают
  те же хвостовые знаки), `s:lstrip('/')` вместо `s:gsub('^/+', '')`;
- **бросок без места — одним помощником:** `error(message, 0)` имеет
  неотличимый мутант `0-1`, и правило на него нужно на каждой такой
  строке. Один помощник `raise(value)` с этой строкой внутри — и правило
  одно на весь проект. Бросок только ради выхода из своего `pcall`
  заменяется возвратом пары `nil, err`;
- **условие, оба исхода которого ведут к одному ответу,** — знак, что
  ветка лишняя: убрать её проще, чем глушить.

Если строка выглядит проверенной, не будучи ею, — это повод изменить код,
а не список исключений.

## Замки и уборка

**Замок прогона** (`var/mutants/lock`). Во время прогона исходники
подменены мутантами: правка файла в это время либо потеряется
при восстановлении, либо исказит результат, и понять это по симптомам
почти невозможно — тесты начинают падать там, где их никто не трогал.
Второй запуск рядом с живым прогоном отказывает, ничего не трогая. Замок
без живого анализатора — след обрыва, он снимается сам.

**Замок машины** (`/tmp/tnt-mutants-machine.lock`). Копий проекта бывает
несколько, но процессор один: два прогона сразу идут втрое дольше и,
что хуже, врут — тесты не укладываются в срок анализатора, и убитый
мутант числится выжившим. Прогоны выстраиваются в очередь по общему замку
и ждут своей очереди сами (до `MUTANTS_QUEUE_WAIT`, час).

**Каталог узлов luatest** (`MUTANTS_VARDIR`). Умолчание у luatest —
общий `/tmp/t`. Когда копий проекта несколько, каждая вычищает этот
каталог под собой и уносит узлы соседей; чужие файберы застревают, цикл
событий пустеет, и luatest выходит с нулём посреди набора — живой мутант
объявлен убитым. Утилита задаёт свой каталог, считанный от пути проекта
и короткий: в длинный путь не влезает адрес управляющего сокета, и узел
не поднимается.

**Уборка.** Оригиналы исходников кладутся в сторону и возвращаются
на место при любом исходе, включая Ctrl-C; прерывание завершает прогон,
а не только зовёт уборку. Убирает за собой только тот, кто взял замок:
запуск, отказавший до замка, не снимает чужой замок и не возвращает
исходники посреди чужого анализа. Процессы Tarantool, оставшиеся
от прогона — узлы в каталоге узлов и luatest в корне проекта, —
гасятся; другие процессы в корне проекта, например узлы приложения,
поднятые для разработки, не трогаются.

**Оборванный прогон.** Прогон, убитый без шанса прибраться, оставляет
исходник подменённым мутантом, а рядом — его копию с суффиксом
`.um.backup`. Следующий запуск находит такие копии до всего остального,
возвращает исходники на место и называет их: «Восстановлен после
оборванного прогона». Без этого следующий прогон падал бы на базе, тесты
валились бы в местах, которых никто не трогал, а при неудачном стечении
мутант уехал бы в коммит.

## Рабочий каталог

Всё, что порождает прогон, лежит в `var/mutants/` (`MUTANTS_WORKDIR`);
корень проекта остаётся чистым. Каталог стоит добавить в `.gitignore`.

| Файл | Что там |
|---|---|
| `generated/` | мутанты текущего файла и списки убитых/выживших |
| `backup/` | оригиналы исходников на время прогона |
| `run-tests.sh` | сгенерированный исполнитель прогона |
| `runner.out` | вывод luatest последнего прогона |
| `gen-<файл>.log` | полный вывод генератора: отброшенные правила, пропущенные строки |
| `analyze-<файл>.log` | полный вывод анализатора: каждый мутант и приговор |
| `timeout-<файл>.log` | мутанты, убитые пределом времени |
| `launch-<файл>.log` | мутанты, на которых проверки не запустились |
| `lock` | замок прогона |

Имя файла в журналах — его путь с `@` вместо `/`.

## Самопроверка

Утилита не кричит, когда ломается, — она молча перестаёт смотреть,
и цифра остаётся зелёной. Глушитель `return\s+\w+`, пара комментария
в литерале, неизвестный аргумент luatest, файл без мутантов и набор длиной
почти в предел мутанта — каждое такое пятно способно жить неделями, потому
что заметить его нечем. Поэтому у утилиты есть своя проверка:
`tnt-mutants selftest` (`selftest/run.sh`, около 25 с). Она гоняет
утилиту по образцам `selftest/samples/`, итог которых известен заранее,
и сверяет его в одиннадцать шагов:

| Шаг | Образец | Что обязан показать прогон |
|---|---|---|
| 1 | — | `--list` не находит образцов; несуществующий файл — отказ |
| 2 | `returns.lua` | мутанты на `return true` и `return value`, двое выживших в отчёте; на `return Module` и `return nil` мутантов нет |
| 3 | `blind.lua` | строки с парами названы, потерянные строки названы, отказ «слепое пятно», «мутанты кончились на строке N» |
| 4 | `skipped.lua` | «генератор пропустил строк: 1» с номером строки уровня у многострочного `error(..., 0)` |
| 5 | `empty.lua` | ноль мутантов — отказ; из списка — принят; лишняя запись в списке — отказ; база для двух файлов одного набора идёт один раз; названный явно несуществующий список — отказ |
| 6 | `returns.lua` | с аргументом `--failure` прогон падает на проверке базы, до мутантов не доходит |
| 7 | `returns.lua` | набор, пропавший после базы, даёт «проверки не запустились на мутантах: 3» и отказ при ста процентах |
| 8 | `returns.lua` | неразборчивое правило в копии `lua.rules` останавливает прогон |
| 9 | `skipped.lua` | дробный срок — отказ; база со сном 1,2 с при пределе 2 с: с явным `MUTANTS_TIMEOUT` — отказ до генерации мутантов с именем набора и нужным сроком, со сроком по умолчанию — «предел мутанта поднят» и прогон проходит; база дольше `MUTANTS_BASELINE_LIMIT` — отказ |
| 10 | `returns.lua` | проверка, зависающая только под мутантом: три мутанта убиты пределом, «убито пределом времени: 3», список сохранён |
| 11 | `ignored.lua` | со своим списком правил: мёртвое и неразборчивое — отказ с местом каждого в списке (`путь:строка`), анализ дошёл до конца; живое глушит свою строку и не названо; широкое глушит обе строки и названо с номерами; правило чужого файла не судится; без мёртвых правил прогон проходит; несуществующий список — отказ |

Для этого у утилиты есть подмены, нужные только самопроверке:
`MUTANTS_RULES`, `MUTANTS_LUATEST_FLAGS`, `MUTANTS_EMPTY_LIST`,
`MUTANTS_IGNORE`, `MUTANTS_DEFAULT_TIMEOUT` (подъём предела над
пятнадцатью секундами иначе проверялся бы восьмисекундным набором).
Проверки шагов 9 и 10 спят и зависают только на базе или только под
мутантом — по переменной `CURRENT_MUTANT_SOURCE`, которую задаёт
анализатор; утилита её при запуске сбрасывает, чтобы унаследованная
снаружи не выдала базу за мутанта.

Образцы в обычный прогон утилиты не попадают: её собственный
`mutants.conf` исключает `selftest/`, и первый шаг самопроверки следит
за этим сам.

## Подключение к проекту

Цель в `Makefile` проекта:

```make
.PHONY: mutants
mutants: ## Мутационное тестирование изменённого кода
	tnt-mutants

.PHONY: mutants-file
mutants-file: ## Мутации по одному файлу: make mutants-file FILE=src/a.lua
	tnt-mutants $(FILE)
```

В хуке pre-push прогон идёт по изменённым файлам ветки — это и есть
режим без аргументов. В `.gitignore` проекта — `var/mutants/`.

## Ловушки

Каждая проверена на живом коде:

- `tarantool -e '<код>'` после выполнения уходит в интерактивный режим
  и висит — в команде проверки мутанта обязателен `os.exit(0)`;
- сторож предела времени гасится всей своей группой процессов
  и с отвязанным выводом: осиротевший `sleep` держал бы канал, и проверка
  базы, читающая вывод исполнителя, ждала бы его весь предел;
- прогон под мутантом запускается своей группой процессов и гасится
  по пределу вместе с ней — иначе убить можно только сам luatest, а узлы,
  которые он поднял, остаются сиротами;
- генератор и анализатор оставляют рядом с исходниками `*.um.backup.<pid>`
  и в корне `.tmp_mutant.*`; они удаляются утилитой, а до её уборки могут
  попасться линтеру или поиску дублей;
- первая строка отличия мутанта берётся `awk`, а не `head`: `head`
  закрывает поток на первой же строке, `diff` получает SIGPIPE,
  и под `pipefail` это молча убивало бы прогон сразу после генерации;
- код возврата `diff` на различающихся файлах равен единице, а мутант
  отличается от исходника всегда — под `pipefail` эта единица роняла бы
  подсчёт, и предупреждение о ранней остановке мутантов не печаталось бы
  ни разу.
